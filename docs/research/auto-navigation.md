# 调研：基于设备图像的「雷达扫图 + 障碍标记 + 开放世界自动寻路」

> 版本 v1 · 日期 2026-10-13 · 状态：**待拍板**（先调研，未写实现代码）
> 目标：回答「能不能做」；盘点可参考/可抄的开源实现；给出与本仓库约束（D6：只用 Apache/MIT）兼容的架构与分期。
> 相关：`docs/DESIGN.md` §0.2 D6（许可证约束）、§1 非目标（不做注入/内存读写）、§7 状态图 DSL。

## 0. 结论先行

1. **能做，但「实时雷达建图 + A\*」这个形态在成熟项目里不存在**，也不该做。
   所有能长期无人值守跑起来的开源方案，骨架都是同一套：
   **小地图定位（图像匹配得到世界坐标+朝向）→ 预建地图/预录路线 → 路径跟随（闭环纠偏）→ 卡死脱困/传送恢复**。
2. 「雷达扫图」这个设想本身是成立的，但要拆成两件不同的事：
   - **静态可通行域**：一次性从游戏大地图/交互地图刷出可行走栅格 + 障碍掩码（半自动，人工确认）。这是主力，稳定。
   - **动态占据栅格**：从小地图/雷达画面做颜色或语义分割，按位姿投影进栅格，用于**局部避障和临时封路**，不是用来建全局地图。这是加分项，做在后期。
3. **第三人称 3D 开放世界，仅凭单目 RGB 画面无法稳定重建全局障碍地图**（没有深度、没有尺规、遮挡严重）。做 SLAM/视觉建图成本极高且脆弱，明确不推荐。
4. **许可证是硬约束**：BetterGI / StarRailCopilot / AzurLaneAutoScript / minimap / ok-ww 全是 GPL-3.0 或 AGPL-3.0，
   按 D6 **一行代码都不能抄**，只能读思路后自己重写。唯一 MIT 的成熟参考是 **cvAutoTrack**（Windows C++ DLL），
   可以看算法、看它要求的游戏设置，但落地上建议用我们已经有的 OpenCV 自己实现（它的核心就是模板匹配 + 亚像素 + 尺度搜索）。
5. **投入产出比最高的落地顺序**：先做「自截地图 + 手动标可行走 + 小地图模板定位 + A\* + 纯追踪跟随」，
   在固定 16:9 分辨率下能做到「点一个坐标，角色自己走过去」。这一条通了，再谈多地图、路线录制、动态扫描。

## 1. 把「雷达扫图」翻译成可实现的三个功能

你描述的东西，在屏幕视觉的约束下其实是三个互相独立的能力：

| 你的设想 | 可实现形态 | 依赖 | 难度 |
|---|---|---|---|
| 雷达扫图，知道周围有什么 | **小地图/雷达 ROI 提取 + 可通行色分割**，按当前位姿投影成本地占据栅格 | 需要先有位姿（定位） | 中 |
| 标记障碍/不可走区域 | **栅格掩码编辑**：一张世界地图底图 + 一张可行走掩码（画笔刷/自动刷/从截图生成） | 不需要定位 | 低 |
| 开放世界自动寻路 | **全局 A\* 规划 + 局部纯追踪跟随 + 卡死恢复** | 定位 + 栅格 + 控制 | 中 |

关键依赖关系：**没有定位，扫图就没有坐标系**；所以定位是整个模块的地基，必须第一个做。

## 2. 可行性边界：先分清游戏形态

| 游戏形态 | 典型 | 小地图/雷达 | 可行能力 | 不建议承诺 |
|---|---|---|---|---|
| **A. 有全局地图 + 小地图的 3D 开放世界** | 原神、鸣潮、星铁（区域制） | 有，圆形/方形，可锁定方向 | 全局定位、跨区域路线、采集/刷本路线、传送图 | 「自动探索全图」「未知区域自动建图」 |
| **B. 俯视/斜俯视 2D、小地图即全局** | 暗黑类、部分手游 | 画面本身就是俯视 | 占据栅格建图很准，能真做「扫图」+ 前沿探索 | 复杂 3D 地形（高度、跳跃） |
| **C. 无小地图，只有第三人称视角** | 部分主机/PC 3D 游戏 | 无 | 只能做**视觉示教**（人开一遍，机器跟一遍）+ 反应式避障 | 任何形式的全局地图重建 |

原神类（A）是所有开源脚本的主战场，也是这套方案的主目标。**先把 A 做通，B 是自然延伸，C 只做示教回放。**

## 4. D6 约束下「能抄什么」

按 `docs/DESIGN.md` §0.2 D6，本项目只允许 Apache/MIT 依赖，不引入 AGPL/GPL 代码（要保留闭源分发可能）。
所以：

- **可以抄的**：算法思想、数据结构、参数经验、游戏设置要求。著作权保护的是具体表达，不是算法。
- **不能抄的**：上面 GPL/AGPL 项目里的任何源码、注释、常量表、资源文件（包括 BGI 的地图掩码图片、路线 JSON 数据）。
  照着重写时不要「边看边逐行翻译」，容易构成衍生作品；建议先看懂→合上→自己写→再对照测试。

## 5. 推荐架构

### 5.1 分层

```
L5 任务层   flow engine 的 navigate 步骤 / 路线任务（采集、刷本、跑图）
             ↑ 到达/失败/卡住 事件
L4 跟随层   pure pursuit：位姿+路径 → (转视角, 前进/摇杆) ；卡死检测 → 脱困阶梯
             ↑ 路径
L3 规划层   栅格 A*（粗网格全局 + 细网格局部）+ 视线捷径平滑 + 传送图边
             ↑ 栅格/代价
L2 建图层   静态可行走掩码（人工/半自动）+ 动态占据栅格（小地图扫描投影）
             ↑ 位姿
L1 定位层   小地图 ROI → 世界坐标 (x,y) + 朝向 θ + 置信度（模板匹配 + 先验 + 亚像素）
             ↑ 帧
L0 采集层   复用 session 的唯一截图循环；小地图 ROI 归一化裁切
```

### 5.2 模块落位（建议）

```
engine/src/gamepilot/nav/
├── __init__.py
├── model.py        # NavMap / Grid / Poi / Route / Pose 数据类（坐标一律归一化或米）
├── minimap.py      # ROI 提取、圆/方遮罩、颜色先验、缩放归一
├── localizer.py    # 模板匹配定位 + 相位相关先验 + 亚像素 + 置信度
├── occupancy.py    # 小地图分割 → 栅格投影（动态障碍）
├── planner.py      # A*/JPS、代价场、视线平滑、传送边
├── follower.py     # pure pursuit、转向标定、卡死检测
├── recovery.py     # 脱困阶梯、传送回退
├── controller.py   # 与 session 帧循环/输入锁对接的异步控制器
└── calibrate.py    # 分辨率/缩放/朝向 标定流程
```

新增 RPC 前必须先改 `engine/src/gamepilot/protocol.py`（`docs/CONVENTIONS.md` §5 有 pytest 守门：
方法名必须同时出现在 `docs/rpc.md` 与 `apps/desktop/src/lib/rpc.ts`）。新增 flow 步骤要同步
`STEP_KINDS` ↔ `FLOW_STEP_TYPES`，否则测试直接红。

### 5.3 与现有引擎的接缝（重要）

现在引擎是「每拍识别 → 选一条边 → 执行一个动作」，导航是**长时闭环控制**，节奏不一样。三个必须处理的问题：

1. **帧来源**：不能自己开截图循环（`session.py` 规定每设备唯一循环）。导航注册成帧消费者，从 session 拿最新帧，丢帧就用上一帧。
2. **输入所有权**：导航发键鼠/摇杆时，flow engine 不能再点。加一把「输入租约」：`navigate` 步骤开始时取租约，结束/取消时释放；期间 flow engine 只允许 recovery 边打断。
3. **阻塞语义**：`navigate` 是阻塞步骤，但必须可取消、可超时、可被 recovery 打断。事件走通知（`nav.pose` 10Hz、`nav.progress`、`nav.stuck`、`nav.arrived`、`nav.failed`），不要塞进 `engine.frame` 那个高频通道。

## 6. 关键算法（够写到能实现的程度）

### 6.1 L1 定位：小地图 → 世界坐标

参考 StarRailCopilot wiki 公开的算法要点（**思路可学，代码不可抄**），加上我们自己的先验：

1. **ROI**：小地图位置随分辨率缩放，用归一化矩形 `roi` 配置；圆形小地图先做圆遮罩，去掉边缘 UI。
2. **预处理**：转灰度 → 降采样到固定宽（如 256px）→ 可选 Canny（星铁这类低对比地图用边缘图匹配更稳）。
3. **先验搜索**：维护上一帧位姿 `p_{t-1}`；用相邻两帧小地图做 `cv2.phaseCorrelate` 估出帧间位移 `Δ`，
   预测 `p̂_t = p_{t-1} + R(θ)·Δ`。只在 `p̂_t` 周围 ±40px 的窗口里匹配 —— 这是**性能与抗歧义的关键**，
   也直接解决「空旷区域误匹配」。
4. **尺度**：小地图比例会随奔跑/缩放变化（星铁是渐变的）。维护一组候选尺度 `[0.9, 0.95, …, 1.25]`，
   取分数最高者，且**加迟滞**（新尺度要连续 3 帧胜出才切换），避免抖动。
5. **匹配**：`cv2.matchTemplate(map_gray, tmpl, cv2.TM_CCOEFF_NORMED)`；候选窗口内取局部极大值
   （`result - GaussianBlur(result)` 再取 max），避免大片相似区域选错峰。
6. **亚像素**：把分数矩阵用 `INTER_CUBIC` 放大 10~20 倍再取 argmax（StarRailCopilot 的做法，简单有效）；
   或对 3×3 邻域做二次曲面拟合。
7. **朝向 θ**：两条路——
   - 便宜：颜色分割出小地图上的角色箭头，取质心相对小地图中心的向量；
   - 稳：0~360° 箭头模板拼成一张大图，拿小地图箭头去匹配（模板匹配次数从 N 降到 1）。
8. **置信度**：`conf = score × 峰值锐度`（峰值减去邻域均值）。`conf < 0.5` 连续 3 帧 → 进入 `lost`，
   交给恢复层（先尝试全图搜索，再失败就要求 flow engine 走传送/回已知点）。

**代价估计**：4096² 底图降到 512²，模板 64²，单次 `matchTemplate` 约 2~5ms；10Hz 定位完全够。
**前提**：固定 16:9 分辨率、游戏内「锁定小地图方向」打开（否则要额外估小地图自转）。

### 6.2 L2 建图：静态掩码 + 动态占据

- **静态**（主力）：用户截一张游戏大地图 → 标定 `map_px_per_meter` 与原点 → 用画笔刷可行走，
  或按颜色阈值自动刷（道路/草地可走，建筑/水面/悬崖不可走），人工再修。输出 `walk.png` 掩码。
- **动态**（加分）：小地图 ROI 按游戏配色分成 `free/blocked/unknown` 三类（每游戏一份 palette），
  每个像素按 `world = pose + R(θ)·(px·mpp)` 投到 1m 栅格，`blocked` 需要连续 k 次命中才落笔（迟滞抗噪），
  `free` 可以擦除「临时障碍」。用途：NPC/车辆挡路、临时封路、活动障碍。
- **玩家半径膨胀**：所有障碍按角色碰撞半径（约 0.4~0.6m）做形态学膨胀，否则规划出的路会贴墙卡住。

### 6.3 L3 规划

- 栅格 1m/格。4000×4000m 的地图是 16M 格，纯 Python A\* 不可行 →
  **两级规划**：8m 粗网格跑全局（256k 格，几十 ms），到目标附近（<80m）切 1m 细网格重规划。
- 代价 = 距离 × 地形系数 + 贴墙惩罚（离障碍 <1m 加价）+ 已知危险区加价；启发式用 octile 距离。
- 路径平滑：从起点做视线可达性剪枝（supercover raycast，遇障碍停），把 zigzag 折线压成少量拐点。
- **非平面连接**：传送点、电梯、攀爬点、游泳点做成图的**边**（`mode: teleport/elevator/climb/swim`，带 `cost_s`），
  规划时允许「走到 A → 传送 → 从 B 继续」。这是 3D 开放世界能不能用的分水岭，BGI 的 waypoint 类型就是干这个的。

### 6.4 L4 跟随

- **Pure pursuit**：取路径上距当前位置 `lookahead = clamp(3 + 0.5·v, 3, 8)` 米的点作为目标，
  算期望朝向，先转视角（鼠标/右摇杆增量，需标定 `px_per_degree`），夹角 <5° 再按前进。
- **转向标定**：一次性标定「鼠标移动 N 像素 = 转 1°」，按分辨率存下来；不同游戏各自一份。
- **到达判定**：距目标 < 1.5m 且速度接近 0，连续 3 帧 → `arrived`。
- **卡死判定**：2s 内位移 < 0.5m，或位姿方差极小但输入在发 → `stuck`。
- **脱困阶梯**（照 BGI 的思路自己写）：① 侧移/跳一下 → ② 后退 2m 重规划 → ③ 转 90° 再试 →
  ④ 传送到最近 POI 重新定位 → ⑤ `nav.failed` 交给 flow engine 的 recovery 边。

### 6.5 「自动探索」的诚实结论

- 有战争迷雾/未探索区域（原神大地图就是）的游戏，可以做 **frontier-based exploration**：
  在占据栅格上找「已知自由区与未知区的边界」，选最近 frontier 作为下一个目标点，循环。
- 但纯屏幕视觉下速度极慢（一次只能看一个小地图范围）、容易在复杂地形卡死，**不建议作为首发功能**。
  真要做，也只在「已标定好大区域、只需要补几个角落」时启用。

```jsonc
    "scale_candidates": [0.9, 0.95, 1.0, 1.05, 1.1, 1.15, 1.2, 1.25]
  },
  "grid": {
    "cell_m": 1.0,
    "walkable": "walk.png",          // 白=可走，黑=障碍，灰=未知
    "player_radius_m": 0.5
  },
  "pois": [
    { "id": "tp_windrise", "name": "风起地传送点", "type": "teleport", "world": [1234, 567] },
    { "id": "ore_01", "name": "水晶矿", "type": "collect", "world": [1300, 600], "respawn_s": 259200 }

    { "id": "daily_ore", "name": "每日挖矿", "waypoints": ["tp_windrise", "ore_01"] }

    "free": [[120, 180, 90], [200, 200, 200]],

```

## 9. 分期与验收

| 期 | 内容 | 验收标准（可测） | 估工 |
|---|---|---|---|
| **N0** | 地图模型 + 载入底图 + 手动刷可行走 + A\* + 路径渲染（不接设备） | 在 4096² 底图上点两点，300ms 内出路径且不穿障碍；掩码编辑可保存/重载 | 3~5 天 |
| **N1** | 定位（模板+先验+亚像素）+ 跟随 + 卡死 | 固定 1080p、锁定小地图方向：沿 50m 两点直线走完，横向误差 <2m，到达 <1.5m；定位 10Hz、P95 <10ms；连续 3 次运行无人工干预 | 5~7 天 |
| **N2** | 传送图 + 跨区域路线 + 录制回放 + flow `navigate` 步骤 | 从 A 区域传送到 B 再走到 C，全程一个 `navigate` 步骤完成；中途拔线重连能续跑 | 4~6 天 |
| **N3** | 小地图动态占据栅格 + 脱困阶梯完善 | 遇到 NPC/临时障碍能绕行；人为把角色卡进角落，30s 内自行脱困或回退传送 | 4~6 天 |
| **N4** | 多游戏/多分辨率适配 + 标定向导 + 前沿探索（可选） | 换 1440p 不改配置能跑；换游戏只需换 palette/ROI + 重新标定 | 持续 |

**建议先做一个 1 天的可行性验证（N-1）**：拿一张真机小地图截图 + 一张大地图截图，
跑一次 `matchTemplate` + 亚像素，量出分数、耗时、误差。分数能到 0.7 以上、误差 <2px 就说明这条路成立，
再投入 N0/N1。这个验证不需要动引擎，一个脚本就够。

## 10. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 分辨率/UI 缩放变化 | 模板匹配直接失效 | 一切 ROI 归一化；底图按比例缩放；运行时按分辨率缓存缩放系数；文档写明「固定 16:9」 |
| 小地图随镜头旋转 | 定位/朝向全错 | 要求游戏内开「锁定小地图方向」（BGI/cvAutoTrack 都这么要求）；不支持就自己估自转角（成本翻倍） |
| 空旷区域误匹配 | 角色乱走 | 先验窗口 + 局部极大值 + 置信度门限 + 连续帧确认（§6.1） |
| 3D 地形（悬崖/水/楼梯/电梯） | 2D 栅格规划出「直线穿墙」 | 传送/攀爬/游泳做成图边；栅格只表达「同层可走」；每层一张子图 |
| 卡死/被怪打断 | 挂机中断 | 脱困阶梯 + flow engine 的 recovery 边接管（战斗/弹窗优先） |
| 反作弊/封号 | 账号风险 | 维持「只读屏幕 + 模拟输入」的非目标；不读内存、不改包；文档写清风险自负 |
| 地图数据版权 | 无法随仓库分发 | 底图用户自截；仓库只带格式、示例占位与标定工具 |
| GPL 污染 | 闭源分发受影响 | 只读思路不抄代码；依赖白名单进 CI 检查（可在 `pyproject.toml` 注释登记 license） |

## 12. 附：没有小地图时怎么做（录制建图 / 拼接世界地图）

先把三件事分开，这是整节的前提：

| 东西 | 怎么来的 | 说明 |
|---|---|---|
| **小地图** | 游戏 HUD 自带，**不是录出来的** | 没有就没有，靠录制变不出来 |
| **世界地图底图** | ① 游戏大地图 UI **截图拼接** ② 手工画 ③ 从帧序列拼接（不推荐） | 2D UI 能拼，3D 画面很难拼 |
| **轨迹 / 关键帧** | **人开一遍，机器录** | 这才是「录制」能拿到的东西 |

所以「自己录一个小地图」这个说法要改成：**录轨迹，拼地图**。

### 12.0 先确认是哪一种「没有小地图」

| 情况 | 判断方法 | 对应方案 |
|---|---|---|
| A. 有 HUD 小地图，只是你没开/被挡 | 设置里找「小地图」「雷达」「显示指南针」；或换 HUD 布局 | 开出来就是 §6 那套，成本最低 |
| B. 没有 HUD 小地图，但有**按 M 打开的大地图** | 按键试 M / Tab / 地图图标 | **§12.1 截图拼接**，1~2 天出世界地图 |
| C. 什么都没有，纯第三人称画面 | 既无小地图也无大地图 | **§12.3 关键帧示教**（主力）；想自由寻路再上 §12.4/§12.5 |

绝大多数商业游戏落在 A 或 B。真正落在 C 的，基本只能做「示教回放」，做不到「任意点自动寻路」。

### 12.1 正解一：大地图 UI 截图拼接（唯一真正像「长截图」的场景）

**为什么这个可行**：游戏的大地图界面是**平面 2D UI**——拖动是纯平移、缩放是纯比例、没有透视、没有遮挡、内容不变。
长截图算法的三个隐含前提（纯平移、无遮挡、内容稳定）**全部满足**。这是整份文档里唯一能直接套「长截图」思路的地方。

流程：

1. 打开大地图，固定一个缩放级别，记下地图控件的屏幕矩形。
2. 按网格拖动，**相邻两屏重叠 ≥30%**；每拖一次等 300ms（拖拽有惯性动画），连续两帧差异小于阈值再截。
3. 相邻帧用 `cv2.matchTemplate`（或 `phaseCorrelate`）求纯平移偏移，累加成全局坐标。
4. 拼到大画布上；重叠区用**中值融合**（不是平均）——地图上的玩家箭头、任务图标、队友标记会动，中值能把它们抹掉。
5. 换更高缩放级别再拼一轮，得到高清版；或只拼一轮，够用就行。

工程细节（都是坑）：

- **动态元素**：玩家位置箭头、任务光柱、队友标记、时间/坐标文字。中值融合 + 只取地图控件内部（裁掉边框 UI）。
- **拖拽惯性**：不等稳定就截，偏移会算错；用「连续两帧差 < 阈值」做稳定判据。
- **边缘羽化**：接缝处做 8~16px 线性羽化，否则有硬边。
- **缩放级别对齐**：不同缩放级别之间用特征点（ORB）配准，别用平移。
- **分辨率估算**：1080p 一屏大约覆盖 1/3 地图，3×3 拼接 ≈ 3240×3240，足够做 1m/格的栅格（一张 4km×4km 的地图也才 4000×4000）。

拼完之后还要一步**标定**，把「地图像素」换成「米」：

- 方法一：地图上两个已知传送点的实际距离（游戏 wiki 有）÷ 像素距离；
- 方法二：让角色沿直线跑 T 秒，用速度×时间估距离，再对照像素位移；
- 方法三：网格线（很多游戏大地图有坐标网格）直接读。

**局限**：只能拿到游戏愿意画出来的信息（迷雾区/未探索区是空的）；地图图标会挡地形；多楼层地图要分层拼。

工作量：**1~2 天**，纯 2D 图像处理，不碰 3D、不碰定位，效果还直观（能直接给用户看拼出来的图）。

### 12.2 为什么不能直接拿 3D 游戏画面拼世界地图

「长截图」能成立，靠三个前提。第三人称 3D 画面三条全不满足：

| 长截图的前提 | 3D 第三人称的现实 | 后果 |
|---|---|---|
| 纯平移，无透视 | 透视投影，近大远小，尺度随距离连续变化 | 拼出来尺度对不上，越远越糊 |
| 无遮挡 | 角色本人占屏 20~30%，树/建筑/山体互相遮挡 | 大片空洞和鬼影 |
| 内容与光照稳定 | NPC 走动、天气、昼夜、水面反光 | 接缝撕裂、重影 |
| （隐含）相机朝正下方 | 多数游戏俯仰角锁在 -60° 左右，压不到 -90° | 拿不到真正的俯视图 |

真要硬拼，需要一整套东西：相机内参/外参标定（游戏不给）→ 地面平面单应 warp → 每帧只取近场一条带 → 视觉里程计串位姿 → 回环检测消漂移。
工程量约等于**一个简化版 SLAM**，而且换个游戏就全废。**不推荐**，除非目标游戏是固定俯视角（2D/斜 45°）——那种情况拼接是可行的，因为透视是恒定的。

### 12.3 正解二：关键帧示教（没有大地图时的主力）

思路：**不建图，只记路**。人开一遍，机器把「看到了什么 + 做了什么」记下来；回放时用画面匹配纠偏，而不是靠坐标。

录制内容不是视频，是压缩过的关键帧序列（每 0.5~1m 一帧）：

```jsonc
{
  "route_id": "daily_ore",
  "fps": 10,
  "keyframes": [
    {
      "i": 0,
      "patch": "kf/0000.jpg",          // 归一化裁切的小图（如 320×180），不是全屏
      "features": "kf/0000.orb",        // ORB 描述子（可选，匹配更快更稳）
      "action": { "keys": ["W"], "ms": 850, "turn_deg": 12 },  // 到下一帧之间做了什么
      "checkpoint": true                // 可从这里重新开始
    }
  ]
}
```

回放循环：

1. 取当前帧，与当前关键帧 `i` 做 ORB + 单应（或模板匹配），得到画面偏移 `(dx, dy)` 与匹配内点数。
2. 偏移 → 修正指令：横向偏移大就微调转向，纵向偏移大就调前进时长。
3. 匹配成功（内点 ≥ 阈值）→ 前进到 `i+1`；连续失败 3 帧 → 停下，**回退到上一个 checkpoint** 重试。
4. 仍失败 → 报 `route_lost`，交给 flow engine 的 recovery 边（回主界面/传送/重开）。

优点：**不需要地图、不需要标定、不需要定位**，1~2 周能出可用版本；对采集/刷本/日常这种「固定路线」任务足够。
缺点：只能走录过的路；起点必须在路线附近；光照/天气变化会掉匹配（对策：多时段录多套，或改用边缘/结构特征而非灰度像素）。

### 12.4 正解三：轨迹栅格化（示教 → 可规划地图，性价比最高的折中）

示教只能回放一条线，想「在已探索区域内自由换路」怎么办？**把走过的轨迹直接刷成可行走栅格**：

1. 录的时候按时间采样角色位姿（哪怕只是粗略的「走了多远、转了多少度」的航位推算）。
2. 把轨迹点连成线，按角色宽度（约 1m）膨胀成走廊，写进 `walk.png`（白=可走）。
3. 再人工补几笔（把两个走廊之间的空地刷通），或者让机器在走廊端点做几次「试探性直走」自动延长。
4. 之后就能在这张图上跑 A\*——只能到「走过或补过」的地方，但已经能实现「从 A 走廊任意点去 B 走廊任意点」。

这比 SLAM 便宜一个数量级：**不需要回环检测、不需要尺度标定、不需要特征匹配建图**，因为栅格是「画」出来的不是「算」出来的。
代价是覆盖率靠人，但开放世界脚本的真实需求（采集路线、刷本路线、跑图）本来就集中在几条固定走廊上。

### 12.5 视觉里程计 + 占据栅格（真 SLAM 档，最后再考虑）

如果目标是「任意未知区域自由寻路」，才需要这一档：

- ORB + 本质矩阵/单应估帧间运动；尺度靠「跑步速度 × 时间」标定（游戏里移动速度恒定，可测）。
- 累积位姿 → 把画面下方地面区域投影成 1m 栅格，标记可走/障碍。
- 漂移靠回环检测（关键帧检索 + 位姿图优化）修正。
- 工程量 3~4 周起；对快速转向、跳跃、传送、动态物体非常敏感；换游戏基本重做。

**结论：除非明确要「未知区域自由探索」，否则不做。** §6.5 里对「自动探索」的判断在这里同样适用。

### 12.6 三档能力对照

| 档 | 输入 | 产出 | 能做什么 | 不能做什么 | 成本 |
|---|---|---|---|---|---|
| **T0 示教回放** | 人开一遍 | 关键帧序列 + 动作段 | 固定路线采集/刷本/日常 | 换起点、自由选目标 | 1~2 周 |
| **T1 轨迹栅格 + A\*** | 示教 + 少量手刷 | `walk.png` + POI | 已探索路网内任意点寻路 | 未走过的地方 | +3~5 天 |
| **T2 视觉里程计建图** | 纯画面 | 位姿图 + 占据栅格 | 未知区域建图/探索 | 稳定长期无人值守（漂移） | +3~4 周 |

**建议**：默认按 T0 起步；如果目标游戏有大地图 UI（情况 B），先花 1~2 天拼出底图，直接跳到 §6 的「定位 + A\*」主线（比 T1 更准也更好维护）；只有情况 C 且确实需要自由寻路，才考虑 T2。

### 12.7 对 §9 分期表的修订

在 N0 之前加一个**决策/准备块**：

| 块 | 内容 | 验收 | 估工 |
|---|---|---|---|
| **N-0 地图来源** | 判断 A/B/C；B → 写拼接脚本产出 `map.png` + 标定 `meters_per_px`；C → 先做 T0 示教录制器 | B：拼出完整底图且接缝不可见、标定误差 <5%；C：录一条 50m 路线能原样回放 | B 1~2 天 / C 1~2 周 |

另外 §9 的 N1「定位」在 C 情况下要降级为「关键帧匹配」，不要求全局坐标——这一点实现时要分支，不要硬套同一套 localizer。

## 13. 适配游戏类型：什么游戏真能「扫图 + 寻路」

### 13.1 一个判据：画面是不是「地图」

所有方案的分岔只取决于三个问题：

1. **镜头固定吗？**（固定俯视/斜俯视 ↔ 自由旋转）
2. **屏幕坐标能直接当世界坐标用吗？**（能 ↔ 要靠匹配反推）
3. **地图是固定的，还是每局重新生成？**（固定 ↔ 程序生成）

第 2 条是分水岭：**能**，就真能「扫图 + A\*」（屏幕即地图）；**不能**，就只能「定位 + 预建图/预录路线」。
第 3 条决定建图是「一次」还是「每局一次」。

### 13.2 适配度矩阵

| 类型 | 代表 | 镜头 | 地图 | 适配度 | 该用什么 |
|---|---|---|---|---|---|
| **俯视/斜俯视 ARPG 地牢** | 暗黑 like、以撒、哈迪斯、元气骑士 | 固定 | 程序生成 | **S** | **在线占据栅格 + 房间图 + A\***（唯一能真扫图的形态） |
| **2D 平台跳跃** | DNF、枫之谷、泰拉瑞亚 | 固定侧视 | 部分固定 | A | **平台图**（节点=落脚点，边=跳/落/梯），不是栅格；参考 auto-maple 思路 |
| **固定视角 3D 副本** | WoW/FF14/剑网3 副本 | 自由但地图固定 | 固定 | A | **预建导航点图 + 路线回放 + 触发器**（拉怪点、Boss 站位） |
| **2.5D 斜 45° 3D** | 暗黑 4、失落的方舟 | 固定 | 部分固定 | A− | 栅格可做，但有墙体遮挡 + 高度差，要配房间图 |
| **MOBA（手机端）** | 王者荣耀、英雄联盟手游 | 固定角度跟随 | 固定对称 | A（技术）/ C（产品） | 小地图读点定位 + 手画 lane 图 + 摇杆跟随；但瓶颈在决策不在导航，见 §13.5 |
| **3D 开放世界** | 原神、鸣潮 | 自由 | 固定 | B | 小地图定位 + 预录路线（§3~§9 那套） |
| **横版 3D 动作** | 鬼泣 like | 固定侧视 | 固定 | B | 示教回放为主 |
| **回合制/走格子/塔防** | 明日方舟、云顶、战棋 | 无关 | 显式网格 | **不需要导航** | 网格坐标直接点击，别上视觉寻路 |
| **FPS / PVP** | — | 自由 | 复杂 | C | 不做（对抗 + 反作弊 + 3D 自由视角，三重不利） |
| **竞速 / 音游 / 体育** | — | — | — | C | 不做（纯操作精度，导航无意义） |
| **程序生成 + 高对抗** | 肉鸽 FPS | — | 每局变 | C | 不做（建图来不及，且战斗压过导航） |

### 13.3 「地下城」其实分三种，方案完全不同

「地下城」这个词容易混，先分清：

| 子类 | 代表 | 地图 | 镜头 | 方案 | 真正的难点 |
|---|---|---|---|---|---|
| **暗黑 like ARPG 地牢** | 暗黑、火炬之光、流放之路、以撒 | 每局程序生成，房间+走廊 | 固定俯视/斜俯视 | **在线扫图：房间图 + 房间内栅格 + 前沿探索 + A\*** | 迷雾遮挡、战斗中打断、动态怪 |
| **MMO 副本** | WoW、FF14、剑网3 | 固定、人工设计 | 自由 3D | **预建导航点图 + 路线回放 + 站位触发器** | 拉怪节奏、Boss 机制、团队同步 |
| **肉鸽地牢（房间制）** | 以撒、哈迪斯、杀戮尖塔 | 每局生成 | 以撒固定俯视 / 尖塔是节点图 | 以撒 = 同 ARPG；尖塔 = **图论最短路，不需要视觉** | 决策而非移动 |
| **回合制地牢** | 战棋、暗黑地牢 | 格子 | 固定 | **不需要导航**，点格子 | — |

**关键结论**：如果你说的是「暗黑 like / 以撒」这种**固定俯视 + 房间制 + 程序生成**的地牢，
那反而是整个方案里**最适合**的形态——你最初想要的「雷达扫图 + 标记障碍 + 自动寻路」，在这里是**真能实现的**，
不是退而求其次的「定位 + 预录路线」。

### 13.4 暗黑 like 地牢的完整技术栈（如果选这个做首发）

1. **房间分割**：画面上墙/地板颜色差异明显 → 阈值分割 + 形态学 + 连通域，得到房间块；门 = 房间块之间的窄连通。
2. **房间图（room graph）**：节点=房间，边=门/走廊，边上记「门的位置」。跨房间规划先在这个图上跑（几十个节点，瞬间出结果）。
3. **房间内栅格**：屏幕区域直接按格子投影成 1m 栅格（**固定视角，屏幕坐标≈世界坐标，不用定位、不用标定尺度**），
   墙/岩浆/水按颜色分类，未知区域留灰。
4. **前沿探索（frontier）**：已知自由区与未知区的边界取最近点作为下一目标——这就是「自动探图」，在固定视角下是真的能跑的。
5. **规划**：房间图粗规划 → 房间内 A\* 细规划 → 视线剪枝。
6. **跟随**：屏幕坐标直接算出「往哪个方向走」，甚至可以直接点地面（固定视角下点哪走哪）。**这是最大的省事点**。
7. **战斗中断**：识别到怪 → 交出控制权给现有 flow engine（识别+点击那套），打完再回来继续导航。
8. **拾取**：识别掉落物 → 临时插入 waypoint → 捡完回原路径。

这一套里**没有 SLAM、没有特征匹配定位、没有尺度标定**，因为固定视角把最难的部分消掉了。
工程量估计：房间分割 + 栅格 3~4 天，A\* + 跟随 2~3 天，战斗交接 2 天，**约 1.5~2 周能跑通一个地牢循环**。

风险：迷雾（未探索区全黑，只能靠走进去揭开）、动态怪挡路、在线游戏的反作弊（暗黑 4/POE 是网游，挂机有封号风险；
**首发建议选单机**：以撒、哈迪斯、单机暗黑 like）。

### 13.5 MOBA（王者荣耀 / 英雄联盟手游）：技术最简单，产品最不适合

**归类**：固定角度 + 跟随镜头（中间档）。这类游戏的信息反而是最全的：

- **屏幕 = 局部地图**：镜头角度、俯仰、缩放全固定，只跟着英雄平移 → 屏幕坐标≈局部世界坐标，能扫图；
- **小地图 = 全局缩略图**：固定北向、整张图、自己的点是带朝向的图标 → 直接读全局坐标，甚至不用模板匹配；
- 两者互补，等于同时拿到「全局位置」和「局部障碍」。

**技术上怎么做**（这是全套方案里最省事的一档）：

1. 小地图里按颜色+形状定位自己的点（蓝/绿圆点 + 朝向三角），直接换算全局坐标，精度到「哪个区域」够用；
2. 地图固定且三路对称 → **手画一张 lane waypoint 图**就行，不用扫图、不用 A\*（路径基本是固定的几条线）；
3. 跟随 = 摇杆角度 + 按住时长（固定镜头下方向是稳定的）；
4. 技能/补刀/回城是另一套（识别 + 点击 + 技能轮盘），属于 flow engine 的活。

**但它是产品上的 C 级**：

- **瓶颈不在导航**。MOBA 的难点是决策——打不打、去不去、什么时候回城、团战站哪。导航只占整个问题 10% 左右；
  而 GamePilot 擅长的「识别界面 → 点按钮」恰恰不是 MOBA 的核心。
- **PvP + 强反作弊**。腾讯 ACE/TP 对模拟输入敏感，真人局挂机会被举报；封号成本远高于收益。
- **UI 变动频繁**。版本更新改界面、改英雄、改装备 → 脚本维护成本高，和「长期无人值守」的定位冲突。

**能做且值得做的小范围**（如果一定要碰）：只打**人机模式**刷金币/战令/英雄熟练度、训练营练连招、单英雄固定分路；
不碰真人局。即便这样，收益也有限（金币有上限、战令有任务上限）。

**额外价值**：小地图直接给出真值坐标 → 它是**验证导航模块的好靶子**。可以拿「小地图读到的坐标」当 ground truth，
量自己定位算法的误差（§6.1 的置信度和精度调参就靠它）。这比在开放世界里盲调要快得多。

**一个具体的引擎缺口**：现有 `engine/src/gamepilot/core/actions.py` 的
`ACTION_TYPES = ("click","double_click","long_press","swipe","wait","key","text")` 里，
**没有「持续按住摇杆、方向动态可变」的原语**。`swipe` 是一次性手势，做不了「按住 3 秒、期间不断修正方向」。
要接 MOBA/吃鸡/任何摇杆操作的游戏，得先补 `joystick`（或 `touch_down`/`touch_move`/`touch_up` 三元组）动作类型，
这是比导航模块更前置的改造。

> **已补上（2026-10-18，ADR 0002）**：没有新增动作类型，而是给 `swipe` 加了两个可选参数
> `path`（归一化折线，逐点下发）与 `hold_ms`（到终点后按住不放的时长）。
> 于是「推住摇杆不放」= `path: [[中心], [中心+偏移]] + hold_ms: 2000`，
> 「推住并中途转向」= 多段 `path`；底层走的是 `device.touch` 那条实时通道，
> 所以方向是动态可改的。真闭环走位（边看画面边修正方向）仍然要等 `navigate` 步骤。

### 13.6 推荐首发与理由

**推荐：单机、固定俯视、房间制、程序生成的地牢 ARPG。**

理由：

1. 屏幕即地图 → 「扫图」是真需求，不是噱头，且实现最简单（没有定位这一层）。
2. 每局不同 → 在线建图有真实价值，不是「一次性标完就完事」。
3. 房间制 → 天然的两级规划（房间图 + 房间栅格），性能好、可解释性强。
4. 战斗可交接 → 正好复用现有 flow engine 的识别+点击，不用重造。
5. 失败可恢复 → 回城/重开/下一层，恢复策略简单。

**不推荐首发**：网游副本（反作弊 + 账号风险 + 团队同步）、3D 开放世界（§12.2 已论证画面拼不出图）。

### 13.7 对模块设计的影响

`nav/` 要做成**两种后端共用一个壳**，换游戏只换 adapter：

| 后端 | 适用 | 位姿来源 | 地图来源 |
|---|---|---|---|
| `grid` 后端 | 固定视角（S/A 级） | 屏幕坐标直接映射 | 在线扫图 / 预建栅格 |
| `route` 后端 | 自由视角（B 级） | 小地图匹配 或 关键帧匹配 | 预建底图 / 关键帧序列 |

两者共用：POI/路径/跟随/恢复/RPC/UI。差别只在「位姿怎么来」和「图怎么来」——所以 §5.2 的目录结构不用改，
`localizer.py` 拆成 `localizer_grid.py` / `localizer_route.py` 两个实现即可。
