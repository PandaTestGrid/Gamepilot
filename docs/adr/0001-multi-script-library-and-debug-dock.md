# ADR 0001：多状态图（脚本库）+ 调试信息收进底部抽屉

- **状态**：已接受
- **日期**：2026-10-11
- **决策者**：@mini

## 背景

一个游戏自动化项目通常不止一套流程：日常任务、刷副本、签到、活动……现状是"一个工程目录 =
一份 `graph.json`"，顶栏只有一个简陋的目录下拉（`project.list` 能列兄弟目录，但既不能新建、
复制、重命名，也不能安全删除）。同时调试信息（事件流、时间轴、识别器面板）全挤在右栏，
窗口一矮每个列表只剩两行；日志更是只能去翻终端（打包后根本看不到）。

约束：

- 契约已经稳定：`Project` = 目录（`graph.json` + `templates/`），引擎与文档都以目录为真源；
- 一次只能"跑一套"：运行状态挂在设备会话上（`DeviceSession.running`），每台设备各读一份图；
- 不许引入新的第三方依赖；改动必须可降级（老用户的 localStorage 布局记忆不能把界面打崩）。

## 候选方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. 沿用"一个目录 = 一个状态图"，把库做厚（列表/新建/复制/重命名/回收站） | 契约不动、脚本天然隔离（模板不打架）、引擎改动小 | "一个游戏一个工程"的心智要靠命名约定（`游戏-流程`）来兜 |
| B. 一个工程内多张图（`graphs/*.json`，共享 `templates/`） | 模板共享、切换快 | 破坏 `graph.json` 契约；识别器 label 全局唯一 + 模板同名冲突；迁移与回滚成本高 |
| C. 两级：工程（游戏）> 图（流程） | 最贴近长期使用 | 同时动目录结构、契约、迁移、UI 四层，本轮代价过大 |

## 决定

选 **A**，并同时把"调试区"从右栏搬到**底部可拖抽屉**：

1. **多状态图 = 多个脚本目录**。新增 `project.create / duplicate / rename / delete`，
   四个方法统一返回 `{items, current}`（刷新后的整份列表 + 当前脚本），前端一次调用重绘；
   删除是**移动到 `<库根>/.trash/<名字>-<时间戳>/`**，不做真删除（脚本是用户几小时的劳动成果）。
2. **右栏 Tab 化**：脚本库 / 识别器。两者很少同时看，Tab 省下的纵向空间直接换列表可见行数。
3. **调试信息集中到底部抽屉**：事件流 / 日志 / 控制台 / 时间轴四个 Tab，收起只占 28px；
   引擎日志新增 `engine.log` 通知（stderr 那条路不动），界面里就能看"引擎说了什么"。

不选 B/C 的理由：B 会让 `graph.json` 与 `templates/` 的所有权变模糊（一份模板被两张图引用时，
改哪张图的阈值都影响另一张），而当前模板匹配是核心路径，不值得为省一次"新建目录"冒这个风险；
C 的收益要等真正有"多游戏 × 多流程"的需求时再付代价，届时 A 的库根就是天然的工程边界（可以平移）。

## 后果

- 正面：脚本可复制（调参试错不再怕改坏）、可回收、可切换且切换不打断运行；
  调试不再依赖终端；右栏/底栏各司其职，纵向空间可拖且各自记忆。
- 负面 / 需要接受的代价：
  - 一次只加载一套脚本（要同时跑两套得开两个工程目录 + 两台设备，不在本轮范围）；
  - `.trash/` 会随使用增长，需要人工清理（打印在库面板的说明里）；
  - 事件流只在底部抽屉（不在右栏），关掉抽屉时看不到实时事件。
- 后续动作：
  - 库根（`projects/`）未来可直接升级成"工程"层（方案 C），`project.*` 契约不用改；
  - 帧环形缓冲（M4）接上后，底部抽屉的「时间轴」Tab 换成真实可拖的帧序列。
