# ADR 0002：滑动支持连续轨迹 + 末端保持（摇杆原语）

- **状态**：已接受
- **日期**：2026-10-18
- **决策者**：@mini

## 背景

现有 `swipe` 只能表达**一条直线**：起点 + 终点 + 时长。设备层其实早就有实时触控通道
（`Controller.touch(phase, x, y)`：Android 走 scrcpy 控制通道、iOS 走 HID、macOS 走 CGEvent），
`bezier_trajectory.play_swipe_path` 也能逐点注入 `down / move… / up`，
画面栏拖动控制也是靠它实时发事件的。缺的不是管道，而是**表达**：

- 录不出一条曲线手势（画圈、绕障碍、沿路边走边转视角），抬手时中间几百个点全丢了；
- 表达不了「按住不动一段时间」：`long_press` 是原地按，`swipe` 是一直在动，
  而摇杆要的是「推到某个方向 → **保持** → 松开」；
- 于是任何摇杆类操作（双摇杆射击、赛车、MOBA 走位）都写不出来。

约束：

- 不能新增 `STEP_KINDS`：新增步骤类型要同步前端 `FLOW_STEP_TYPES`、`docs/rpc.md`、
  `docs/DESIGN.md`，还会动到 `test_contract.py` 的三方一致性守门，代价与收益不成比例；
- 老脚本必须原样能跑：`x / y / to_x / to_y / duration_ms` 的语义不能变；
- 归一化坐标铁律不破：轨迹点也是 `[0,1]`，像素换算只在设备层。

## 候选方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. 新增 `stick` 动作类型（原点 + 角度 + 力度 + 时长） | 语义直白，摇杆一看就懂 | 只能表达摇杆，表达不了曲线手势；要动 `ACTION_TYPES`/`STEP_KINDS` 三处契约；角度/力度是设备相关的，换个游戏全要重标定 |
| B. 扩展 `swipe`：多段轨迹 `path` + 末端保持 `hold_ms` | 一套模型同时覆盖「曲线手势」和「摇杆」；完全向后兼容；不动步骤类型 | 摇杆要写成「中心 → 中心+偏移」，用户要理解"推杆 = 一段很短的滑动 + 保持" |
| C. 只保留实时 `device.touch`，不落流程 | 零改动 | 只能人手操作，无法无人值守——而这正是本工具的全部意义 |

## 决定

选 **B**。`swipe` 步骤新增两个**可选**参数：

1. **`path`: `[[x, y], …]`**（归一化，≥2 点）。给了就按这条折线走，`x/y/to_x/to_y` 退化成
   展示用的起点/终点（录制时会一并写，保证老逻辑和摘要仍可读）；不给就还是老的直线 + 贝塞尔。
2. **`hold_ms`: 秒到终点后保持按住的毫秒数**（默认 0）。抬手前 `sleep(hold_ms)`，
   对实时触控通道来说就是**真的按住不放**。

于是三种操作都落在同一个模型里：

| 想做的事 | 写法 |
|---|---|
| 画一个圆弧 / 绕障 | `path` = 曲线采样点，`hold_ms` = 0 |
| 摇杆推向某方向 2 秒 | `path` = `[中心, 中心+偏移]`，`hold_ms` = 2000 |
| 推住并中途转向 | `path` = 多个采样点（每一段都是一次转向），`hold_ms` = 末端保持 |

配套的两个行为修正：

- **时序按弧长分配**，不再"每段均分"。曲线采样点在拐弯处天然更密，均分会让拐弯处突然变慢；
  按累计距离分配才是恒速。（顺带修正了贝塞尔轨迹"参数 t 匀速 ≠ 弧长匀速"的老问题。）
- **录制保留轨迹**：拖动过程中采点，抬手时用 RDP（Douglas–Peucker）简化到 ≤32 点；
  末段静止超过 200ms 就折成 `hold_ms`，剩下的压缩进 `duration_ms`。

不选 A 的理由：`stick` 只解决摇杆，曲线手势还得再开一个类型；而"角度 + 力度"是把设备细节
硬编码进 DSL，换游戏就得重标定，不如直接给轨迹点——轨迹点是与设备/游戏无关的最小信息。

不选 C 的理由：实时触控是**人**在控制，本工具存在的意义是**没人**时也能控制。

## 补记：手势判定不能只看合位移（2026-10-18）

录制端原来用**起止点直线距离**判断「这是滑动还是轻点」。画圈的手势起点和终点几乎重合，
合位移≈0 ⇒ 被判成轻点 ⇒ 整条轨迹被丢弃，用户看到的现象是「画了个圆，回放却是起点到终点的直线」。

现在两个判据任一成立即算滑动：合位移 > `SWIPE_MIN_DISTANCE`，或**实际走过的路程** > 3 倍阈值
（3 倍是为了放过按下时几像素的手抖）。`isSwipeGesture(from, to, threshold, points?)` 多一个可选轨迹参数。

## 补记：UI 用选择框区分两种方式

两种滑动原来挤在同一个面板里（两个录制按钮 + 轨迹行），用户要自己猜"点哪个会写 path"。
现在 `SwipeStepFields` 顶部用「方式」选择框分「点对点滑动 / 连续滑动」，只显示各自的字段：
点对点 = 常用方向 + 起止点 + 录制单次；连续 = 录制连续 + 轨迹缩略图 / 点数 / 清除。

- 选择写进步骤参数 `swipe_mode: 'point' | 'track'`。它是**纯 UI 元数据**：
  `Action.parse` 只读白名单里的键，`flow_model.validate_flow` 也不拒绝未知参数，引擎行为不变。
- 老数据没有 `swipe_mode`，按"有 `path`（≥3 点）= 连续"推断，和补记前的行为一致。
- 切回点对点会清掉 `path`（否则回放仍走旧轨迹）；轨迹行的「清除」只清 `path`、保留 `track`，方便重录。
- 连续方式下有轨迹后不再显示拟人贝塞尔参数：`execute_swipe` 拿到显式 `path` 就直接走轨迹，不套贝塞尔。

## 后果

- 正面：
  - 曲线手势可录可放（画圈、沿墙走、边转视角边走）；
  - 摇杆可持续推住，双摇杆/赛车/走位类操作有了底层原语；
  - 后续自动寻路（`docs/research/auto-navigation.md` L4 跟随）可以直接复用
    `execute_drag`：定位算出路径 → 写 `path` → 推杆，不需要再改设备层。
- 负面 / 需要接受的代价：
  - 轨迹点会让 `graph.json` 变长（一条 2 秒的拖拽简化后约 10~20 点），
    所以**只在偏离直线时才写 `path`**，直滑保持老样子；
  - `hold_ms` 只在实时触控通道下是真保持：adb 兜底通道没有实时能力，
    会把整段（含保持时间）合成一条慢速直线滑动，日志里会告警；
  - 摇杆的"力度"没有建模（`path` 的偏移量即力度），需要用户在游戏里自己校准一次。
- 后续动作：
  - 真要做闭环走位（边走边看画面改方向），在流程层加 `navigate` 步骤，内部反复调 `execute_drag`；
  - 若将来需要"按下但屏幕不动"的语义（例如某些游戏摇杆中心在屏幕外），
    再考虑把 `path` 首点与 `hold` 解耦成 `origin`。
